# Package Management

Goal: Find a way to publish our internal packages in a way that they can be versioned and don't need to be installed/imported by path.
Note that all of this is mostly for internal packages and the cookie-cutter projects. Migration / changes for big projects like `data-model` or the `preselector` are optional and we get there when we get there.

## The Index

Internal packages are stored in a blob container on Azure.
This is what the storage looks like.
```
wheels/                                     # the container, stchefdppkgfeed
├── files/
│   └── chef-0.2.1-py3-none-any.whl
└── links/
    └── index.html
```

The `files/` folder contains wheels for every internal package.
A wheel is an artefact from which you can install a specific version of an internal package.
`links/index.html` is an html file listing every wheel in `files/` along with a pre-signed download url.

```html
<!DOCTYPE html>
<html>
  <body>
    <a href="https://stchefdppkgfeed.blob.core.windows.net/wheels/files/cheffelo_poc_feed-0.1.0-py3-none-any.whl?<SAS>">cheffelo_poc_feed-0.1.0-py3-none-any.whl</a><br/>
  </body>
</html>
```

## Why the HTML?

pip and uv are HTTP clients that expect a package source to tell them what exists. `--find-links` is the simplest format they accept:
Point it at a web page and every `<a href>` on it is treated as a downloadable distribution.
This is the easiest setup for an internal package store. No server involved. Just an html page and links which lead to installable libraries.

## The SAS

Note the `<SAS>` in the html snippet above. It's redacted here, but the real html file contains a SAS (Shared Access Signature) which is basically a read-only access token for the storage account. The SAS is generated by Terraform along with the storage account and stored in KV as [package-feed-read-sas](https://portal.azure.com/#@godtlevertno.onmicrosoft.com/asset/Microsoft_Azure_KeyVault/Secret/https://kv-chefdp-common.vault.azure.net/secrets/package-feed-read-sas/9619a0b92ea74313a40e50175d792eeb).
Using a secret for auth is not ideal, but it's way more convenient. It's also read-only and only give access to the source code of internal packages. So not terribly sensitive.

## Publishing Internal packages

A single github workflow `.github/workflows/package_feed_publish.yml` handles the publishing of internal packages by calling a single script `scripts/package_feed/publish.py`.
It is triggered when a PR modifying anything in `packages/` is merged to main. 
The script handles:
- Listing packages modified by the PR
- Listing packages that are currently published in the index
- Calculating the new version number of the package by getting the latest version published in the index and bumping the patch number by 1.
- Building and publishing the new wheel with the calculated version number.

Some notes:
- The setup is entirely append-only. Any PR changing an internal package will publish a new version of that package. Published wheels are never deleted or overwritten. If a project declares a dependency on a specific version of an internal package, we should never change or delete it. 
- The automatic versioning only ever increases the patch number of the semantic version `<major>.<minor>.<patch>`. Major and minor version numbers are still managed by humans. You should bump the major or minor version of a package if you're making breaking changes to an internal package.
- Upgrading the version of an internal package used in a project is still a manual task involving regenerating the lockfile and re-deploying. There are way to automatically pick up patches that could be worth looking into in the future. Upgrading major & minor versions should always be done manually and tested.

## The switch to UV

We're migrating from `poetry` to `uv` as part of this project and the rework of the Data Science setup. `uv` is faster and cooler than `poetry`.
But that alone doesn't justifying a migration with a fairly big blast radius.
Mostly, we're using `uv` because of two features:

1. `UV_FIND_LINKS`

You can set an environment variable `UV_FIND_LINKS` in your shell with the url to a pip index. `uv` will then look in that index anytime you run `uv add`, `uv lock`, `uv install` etc. This is how we register the internal package feed. If you run `uv add cheffelo-constants`, `uv` will find it in the feed and install that. If you run `uv add pandas`, it will look in the feed, fail to find `pandas` and go look for it in PyPi instead.

```bash
# ~/.zshrc Replace <sas> with the value of package-feed-read-sas in kv-chefdp-common
export UV_FIND_LINKS="https://stchefdppkgfeed.blob.core.windows.net/wheels/links/index.html?<sas>"
```



2. `constraint-dependencies`

__Relevant for a future PR on the DS PoC__
You can add a list of pins under `[tool.uv] constraint-dependencies` in `pyproject.toml`. And `uv add` will respect that. So if you run `uv add pandas` and `"pandas==2.2.3"` is listed in `[tool.uv] constraint-dependencies`, `uv` will default to `"pandas==2.2.3"` instead of whatever the latest version of pandas published is at the time.
This is very convenient for the DS setup because we can template constraints for new projects based on the libraries pre-installed on Databricks serverless.
It's good way to prevent version conflicts or accidentally mutating the serverless environment. Note that it's meant to be a *safe default* rather than a hard rule. 
Everyone is free to pick whichever version of whichever library they want and delete the default constraints in their project. But it's nice to make sure that every project will run fine on Databricks serverless by default.

## Migrating to uv

I'll change the .toml files and the CI/CD for packages to handle both poetry and uv.
We'll start by migrating to `uv` and publishing the first 15 packages that have no internal deps.
Then we'll migrate the remaining 7 packages which have internal deps on some of the 15 packages migrated earlier.

Ideally, all the projects would be moved to `uv` and stop using path deps. However, this does not need to happen right away and I want to limit the blast radius of the changes.
It's better to get the new setup up & running and work on migrating existing projects at our own rythm. 
We still need to make two changes to existing projects to keep everything working as-is:
- Handle the namespacing of packages.
```toml
- catalog-connector = {path = "../../packages/catalog-connector", develop = true}
+ cheffelo-catalog-connector = {path = "../../packages/catalog-connector", develop = true}
```
- Declare transitive dependencies: If packages `A` and `B` are both published on the feed. And package `A` depends on package `B`. And the `A -> B` dependency is not a path dependency (because we got rid of all path deps while migrating the packages.) Then a poetry project that has a path dependency on package `A` needs to explicitly declare a path dependency on package `B`. Otherwise, the project would try to resolve the transitive `A -> B` dependency and fail, because the custom feed is not setup on the poetry project.
It's not very elegant, but it's the best way I've found to get the final setup up & running with minimal changes to existing projects and migration work.

Notes that these two changes will trigger the CI/CD and try to deploy all projects. My plan is to just not approve the prod deploy on the projects that I'm not familiar with. Not because I don't trust that the merged changes to projects are no-op, but because I'm aware of existing bugs or manual work required in the deployment of some ML projects.


## Namespacing

This one is kinda annoying, but we're changing the name of every internal package to prefix them with `cheffelo-`.
```
# sous-chef/packages/slack-connector/pyproject.toml
[tool.uv]
name = "cheffelo-slack_connector"
```

We'll also change the template so new projects and packages created with the chef CLI have prefixed names from the start.
So if you want to add an internal package to your project you'll have to run `uv add cheffelo-constants` instead of just `uv add constants`.

We're doing this to avoid a specific failcase: When adding a package uv will first look into our custom feed, then look on PyPi if the package you're trying to add isn't in the custom feed. The risk is that you try to install a version of an internal package that isn't in the feed for some reason and end up installing a random unknown package from PyPi that happens to have the same name. At best, it's an annoying bug. At worse, it's a security risk, because name squatting on public package repository is a common attack mechanism.
(Fun fact, the libraries `mtplotlib`, `tensoflom` or `reqjuests` on PyPi have all contained malwares at some point to hack people making typos.)
